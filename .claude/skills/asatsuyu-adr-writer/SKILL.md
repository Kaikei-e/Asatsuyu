# Asatsuyu ADR Writer

## ファイル規約

- 置き場所: `docs/adr/NNNN-<kebab-case-title>.md`（NNNN は 4 桁連番。`ls docs/adr/` で既存を確認して次番号を採る）
- 言語: 日本語。コード・型名・クレート名は原文のまま。
- 1 ADR = 1 決定。複数の決定が絡む場合は分割する。
- 既存 ADR（`0001-effect-system-permanent-non-goal.md`, `0002-purity-mechanism.md`）の書き方に合わせる。
  執筆前にどちらか 1 本を Read して粒度を揃えること。

## テンプレート

```markdown
# NNNN: <決定のタイトル>

- ステータス: 提案中 / 採用 / 廃止（→ NNNN で置換）
- 日付: YYYY-MM-DD

## コンテキスト

なぜこの決定が必要になったか。停滞・矛盾・外部状況の変化など、判断を迫った事実を書く。
コードの現状を根拠にするなら、クレート・ファイル・関数名まで書く。

## 決定

何をどうすると決めたか。言い切る。

## 言語憲章との関係

この決定が `docs/concepts/principles.md` のどの節（原則 §3 / 境界 §4 / Non-Goals §8 など）に
触れるか。憲章の改訂を伴う場合は、その diff の要旨をここに書く。影響なしなら「なし」と明記。

## 検討した代替案

退けた選択肢と、退けた理由。先行言語の事例（Gleam / Roc / Elm / ReScript 等）を
根拠にした場合は言語名と該当する設計を具体的に書く。

## 影響・結果

この決定で生じる作業、既存コードへの影響、受け入れるトレードオフ。
将来この決定を覆す条件（threshold）があれば明記する。
```

## 憲章の同時改訂

憲章 §0 は「個別の決定は ADR に記録し、**憲章の本文は同じ変更の中で改訂する**」と定めている。
ADR が憲章の文言を変える・絞る・解釈を固定する場合は、`docs/concepts/principles.md` の該当箇所も
同じ変更で直し、ADR へのリンクを張る（§8 の Effect systems の段落が実例）。
憲章と ADR が食い違ったまま片方だけを残さない。

`docs/roadmap.md` の "What Comes Next" に先送りとして載っている項目の扱いが変わる場合は、そこも直す。

## 置換

既存 ADR を覆す決定は、新しい番号で書き、旧 ADR のステータス行を `廃止（→ NNNN で置換）` に更新する。
採用済み ADR の本文は書き換えない。

## 執筆時のルール

- 忖度なしで書く。「〜かもしれない」でぼかさず、退けた案は退けたと書く。将来の自分が読む文書であり、対外アピール文書ではない。
- 会話の中でユーザーが実際に述べた判断だけを「決定」に書く。Claude が提案しただけで未承認の内容を決定として書かない。
- 決定を覆す条件（例: 「高階関数が非純粋側に倒れて標準ライブラリが実用にならなくなったら再検討」）が会話に出ていたら必ず「影響・結果」に残す。
- `docs/research/` の語彙を現行仕様として引かない。根拠にできるのは憲章・既存 ADR・コード・テスト。
- 文書の記述を根拠にする前に `make docs-sync` で文書と実装の一致を確認する。

## 書き終えたら

- `make docs-sync` を実行して結果を報告する。
- 関連するスライス計画・roadmap への反映が必要かを一行で指摘する。
- commit はユーザの指示があってから。`git push` はしない。
