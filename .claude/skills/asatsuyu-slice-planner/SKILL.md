# Asatsuyu Vertical Slice Planner

計画の唯一の原則: **層を完成させるのではなく、細い機能を最後まで貫通させる。**

## 計画の前に現在地を確認する

記憶や過去の会話ではなく、リポジトリから読む。

1. `docs/roadmap.md` の "Current State" と "What Comes Next" — 何が済み、何が明示的に先送りされているか
2. `docs/concepts/principles.md` §8 Non-Goals と §10 MVP Definition — 入れてはいけないもの、MVP の達成条件
3. `docs/adr/` — 既に決まっていること（Glob で一覧し、関係するものを Read）
4. コードとテスト — roadmap が「まだ無い」と言っていても実装済みのことがある。
   無いと書く前に golden case（`asatsuyu/crates/asatsuyu-cli/tests/cases/`）かコードで確認する

`docs/research/` は探索メモであり契約ではない。そこの Phase 表を現行計画として引かない。

## スライスの定義

1 スライス = 「.asty ソースの特定サブセット → 型検査 → 生成 .py → 実行して動く」までが一気通貫で含まれる作業単位。
どれか 1 段で終わる issue（例:「HIR を拡張する」）は起票しない。必ず emitter と実行確認まで含める。

## 計画時のルール

1. **憲章の判定基準を先に当てる**: 追加しようとしている機能に §11 の 5 つの問いを当て、
   5 番目（言語を派手にするだけ）に該当するなら計画に入れない。
2. **貫通が先、完全性は後**: 推論や検査の網羅性・一般性を最初のスライスに入れない。
   最小の形で end-to-end を通してから、同じ経路を太くする。
3. **各スライスは 1〜3 セッションで完了するサイズ**に切る。それを超える見積りになったらスライスをさらに縦に割る。
4. **Done の定義を必ず書く**: 各スライスに「このスニペットがコンパイル・実行できたら完了」という
   具体的な .asty コード例を添える。その例はそのまま golden case か fixture project になる。
5. **波及先を Done に含めるか、明示的に送る**: 新しい構文は grammar（`docs/grammar.md` は凍結）、フォーマッタ、
   LSP、VS Code 拡張（`editors/vscode/` の tmLanguage・スニペット）に波及する。
   各スライスで「今回やる波及」と「後続スライスへ送る波及」を分けて書く。黙って落とさない。
6. **文書の同期をスライスに含める**: 診断コード・FFI 分類・fixture・CLI フラグに触れるスライスは
   `make docs-sync` が通ることを Done に入れる。
7. **Non-Goal 由来の作業を混入させない**: 計画項目が憲章と整合するか迷ったら grill-with-docs で照合する。
   憲章の解釈を変える必要があるなら、実装計画の前に asatsuyu-adr-writer で決定を記録する。

## 出力形式

計画は次の表形式でまとめる:

| # | スライス名 | 貫通する機能 | Done の定義（.asty 例） | 今回の波及 / 送る波及 | 見積り |
|---|---|---|---|---|---|

表の後に、意図的に**入れなかった**ものとその理由（後回し / Non-Goal）を必ず列挙する。
入れなかったものの明示は、将来の自分がスコープクリープに気づくための記録である。

計画の提示は実装の許可ではない。ユーザの同意を得てから着手し、着手時は tdd-workflow に従う。
issue の起票（`gh issue create`）はユーザの明示指示があってから行う。

## 停滞の検知

同じスライスが 3 セッション以上進んでいない場合、計画の続行ではなく次を提案する:
(a) スライスをさらに薄く割る、(b) そのスライスの前提にあるコンセプト矛盾を疑い grill-with-docs で再点検する、
(c) 判断を asatsuyu-adr-writer で記録して別スライスへ移る。
