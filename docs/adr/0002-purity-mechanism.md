# 0002: 純粋性の機構を呼び出しグラフ上の不動点 + opt-in 宣言とする

- ステータス: 採用
- 日付: 2026-07-28

## コンテキスト

[ADR 0001](0001-effect-system-permanent-non-goal.md) は type-and-effect system を
永久 Non-Goal と定義したうえで、純粋性区別そのものは Non-Goal ではないと明記し、
その実現機構を 2 案に絞って先送りした。

1. 単相の型レベルマーカー — `Task(T)` と同じく戻り型を型構築子で包む
3. 呼び出しグラフ上の不動点計算 — 関数に 2 値属性を与えて単調に伝播させる

判断材料として要求されていたのは「高階関数を含むプロトタイプの実測」である。
その実測は `asatsuyu-hir/src/purity.rs` と `tests/purity_measurement.rs` として
既に入っており、examples コーパスに対して次の結果が出ていた。

- 高階呼び出し箇所（関数型パラメータ／ローカルの適用）は **0 件**
- 未解決呼び出しが記録された関数は 3 つだけで、いずれも別の理由で既に Effectful

つまり ADR 0001 が threshold として挙げた「`map` / `filter` / `fold` 相当が
すべて非純粋側へ倒れて標準ライブラリが実用にならない」状態は発生していない。

一方で、実測プロトタイプは**完全推論**であり、これだけでは診断が 1 件も出ない。
推論は矛盾を起こさないからである。「純粋関数から副作用関数を呼ぶとエラー」を
成立させるには、推論結果と食い違いうる宣言が要る。この宣言をどこに置くかが、
機構選択と同時に決めるべき残りの論点だった。

## 決定

純粋性の機構を次の 4 点で確定する。

1. **解析は呼び出しグラフ上の単調不動点**（選択肢 3）。束は `Pure ⊑ Effectful` の
   高さ 1 で、逆呼び出しグラフ上の worklist が `O(V + E)` で収束する。
   `Ty::Function` には効果スロットを追加しない。
2. **解析は保守的**。呼び出し先を静的に特定できない箇所は
   `EffectSource::Unresolved` として Effectful に倒す。`Pure` は「到達可能な効果が
   無いことの証明」を意味し、楽観的推測ではない。
3. **宣言面は opt-in の `pure` 修飾子**。`FnDef = Visibility? FnModifier* 'fn' ...`、
   `FnModifier = 'pure' | 'async'`。`pure` は `is_async` と同じ関数属性として
   HIR → THIR を貫通し、型には載らない。宣言した関数だけを検査する。
4. **伝播規則は「推論で足りる」**。`pure fn f` の検査は「f から到達する全関数の
   推論結果が Pure」であり、呼ばれる側に `pure` 宣言を要求しない。

診断は `E0154`（`pure` 宣言が効果に到達）と `E0155`（`pure` と `async` の併記）。
`E0154` は効果の到達経路を全ホップ分 secondary label で出す。

## 言語憲章との関係

本リポジトリの上位権威は `docs/concepts/principles.md` であり、`CONCEPT.md` は
作成しない（ADR 0001 の判断を踏襲する）。

憲章の改訂は不要。本決定は憲章 §8 が「純粋性区別は Non-Goal ではない、機構は未決」
と書いた空白を埋めるものであり、Non-Goals の範囲を動かさない。

各原則との関係:

- §2 評価軸第 1 位「型エラーメッセージの品質」— 効果変数が型に入らないため、
  型エラーに効果が漏れない。`E0154` は効果の到達経路を明示する
- §3 原則 1「Clarity over brevity」— `pure` は関数シグネチャに現れる
- §5「生成 Python の透明性」— `pure` は生成物に一切現れない。属性は消える
- §7「型システムの責務」— Hindley-Milner の範囲を出ない

## 検討した代替案

**選択肢 1（単相の型レベルマーカー）を採る。** 却下。純粋性を戻り型の構築子で
表現すると、既に効果を戻り型で表現している `Task(T)` と二重の効果チャネルになる。
ADR 0001 が「統合を検討する義務が生じる」と警告していた事象そのものであり、
`Option(T)` / `Result(a, e)` と並ぶ位置に効果専用の構築子が増える分、
生成 Python の型注釈にも影響が出る。得られる表現力（高階の効果多相）は、
実測で高階呼び出しが 0 件だった以上、いま払う代価に見合わない。

**呼ばれる側にも `pure` 宣言を要求する（viral 方式）。** 却下。安全側に見えるが、
先行例が揃って失敗モードを報告している。

- Rust の const 安定性は再帰的で、`#[rustc_const_unstable]` な関数は stable コード
  から間接的にも呼べない。rustc の開発者自身が「stable な const fn のヘルパーとして
  使うだけの private / unstable 関数にまで `#[rustc_const_stable]` を付けねば
  ならないのは不可解だ」と書いている。ただし Rust が再帰要求を**必要とする理由は
  公開クレート境界をまたぐ API 安定性保証**であり、Asatsuyu にパッケージレジストリ
  は無い（憲章 §8 Non-Goal）
- D はこの失敗モードを "attribute soup" と名付け、属性推論を "D's most important
  tool in avoiding" それだとしている。そして D が通常関数で推論を**しない**理由は
  「通常関数は関数プロトタイプで定義と分離して宣言できるから」であって、
  Asatsuyu にプロトタイプは無い。全関数の本体がコンパイル対象モジュール内にある

モジュラ解析が買えるのは「ライブラリ要約の再利用」と「インクリメンタル解析」だが、
どちらも `docs/roadmap.md` の "What Comes Next" で先送り中である。viral 化が買う
ものを、いま使えない。

**呼び出し側マーキング（`!` 接尾辞などで副作用呼び出しに印を付ける）。** 採らない。
効果が呼び出し箇所ごとに見える点は憲章 §3 原則 1 に最も強く合うが、
ADR 0001 が「特定言語の設計をそのまま移植しない」と明記済みであり、
全呼び出し箇所の書き換えを要求する割に、得られる情報は `E0154` の到達経路表示で
代替できる。

**宣言を設けず報告のみに留める。** 却下。構文を増やさず `asatsuyu check` が
純粋／非純粋を一覧するだけの案。強制力がゼロで、「デフォルトで健全」という
方向性に何も寄与しない。ただしこの案の内容自体は `check --purity` として
併存させた（宣言の有無に関わらず全関数を可視化する）。

**未解決呼び出しを楽観的に Pure のまま扱う。** 却下。プロトタイプの初期実装が
これだったが、`p.exists()` を含む関数が `pure` を名乗れてしまい、宣言が保証に
ならない。保守的に倒す代価は実測でゼロだった（corpus スナップショットが不変）。

**解析を `asatsuyu-ty` 側に移して受け手の型を使う。** 却下ではなく先送り。
`ReceiverUntyped` は推論後なら解ける。ただし現状それを解かなくても精度損失が
無いため、`purity.rs` は `asatsuyu-hir` に留め置く。

## 影響・結果

- `pure` の追加で Hard キーワードが 14 個（全 18 個）になった。`docs/grammar.md` を更新
- `ThirFnDef` に `purity` / `declared_pure` を型情報と並べて保持する
  （`asatsuyu-compiler-dev` の規約「THIR には purity を第一級で持たせる」に従う）。
  `Ty::Function` は不変
- `lower_to_hir` が解析と検査を実行し、`HirLowerResult.purity` を返す。
  `asatsuyu-ty` は THIR 構築のために解析をもう一度走らせる。線形パス 2 本であり、
  25 箇所ある `check_types*` の呼び出し規約を変えるより安い
- `pure` を書いた関数だけが検査対象なので、既存の examples と fixtures は無変更で通る
- 受け入れるトレードオフ: 末端関数を後から非純粋にすると、離れた場所の `pure fn` が
  壊れる。D が「推論失敗時に問題が 10 層下に埋もれる」と報告した現象そのもの。
  `E0154` が効果の到達経路を全ホップ出すのは、この緩和が目的である

**この決定を覆す条件（threshold）**:

1. cross-module 型検査またはインクリメンタルコンパイルを実装する時点で、
   モジュール境界をまたぐ純粋性を推論で解決できなくなる。そのとき初めて
   「モジュール境界でのみ宣言を要求する」形を再検討する
2. 高階呼び出しが実コードで増え、`corpus_has_no_opaque_function_application` が
   落ちるようになった場合、保守的近似の代価を再測定する。`purity_measurement.rs` の
   `every_effectful_function_reaches_a_proven_effect` がその計測器である

の項目を外し、本 ADR へのリンクに置き換える（対応済み）。
